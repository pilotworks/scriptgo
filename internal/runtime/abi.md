# Native Runtime ABI

This document defines the boundary between native code generated by `scriptgo`
and the runtime services available to that code. It is the runtime contract,
not a description of TypeScript or JavaScript semantics. TypeScript parsing,
binding, module resolution, and type checking remain owned by TypeScript-Go;
the reference interpreter remains in [`internal/interpreter`](../interpreter/).

The repository currently implements only the MVP host C ABI. The linked runtime
described in the future sections is a design constraint for later work, not an
implemented library or a stable public ABI.

## Scope And Status

| Area | MVP status | Current implementation |
| --- | --- | --- |
| Process startup | Implemented by the host toolchain | Clang supplies the platform entry point and calls generated `main` |
| Numeric output | Host C ABI | `printf("%g\\n", value)` |
| String output | Host C ABI | `puts(value)` |
| Boolean output | Compiler-generated static strings + host C ABI | Selects `"true"` or `"false"`, then calls `puts` |
| Managed values | Not implemented | No runtime object, array, string, or error library exists |
| Ownership and cleanup | Not applicable to MVP literals | No runtime allocation is performed |
| Runtime errors | Not implemented | Lowering and backend errors stop compilation; libc return values are ignored |
| ABI versioning | Not implemented | The host C ABI is a temporary implementation detail |

The runtime package must not become a second interpreter, a TypeScript
front-end, or a collection of backend helpers. A new runtime operation belongs
here only when its native representation, ownership, failure behavior, and
tests are specified.

## MVP Contract

### Calling convention

The LLVM backend emits opaque-pointer LLVM IR and relies on the platform C ABI
selected by Clang. It declares these external functions:

```llvm
declare i32 @printf(ptr, ...)
declare i32 @puts(ptr)
```

The generated program defines a zero-argument `main` function as `i32` in LLVM
IR. The source-level IR models it as a void function; the backend adapts it to
return `0` to the host process. User-defined functions use the source-level
parameter and return types converted by the backend and are not runtime ABI
functions.

The generated code must use the target's normal C calling convention. It must
not assume a fixed register assignment, pointer width, endianness, or C library
implementation beyond what the selected Clang target provides.

### Native type mapping

The MVP mapping is:

| IR type | LLVM type | Runtime representation | Notes |
| --- | --- | --- | --- |
| `number` | `double` | IEEE-754 binary64 value | Ordinary arithmetic uses LLVM floating-point operations |
| `string` | `ptr` | Pointer to a NUL-terminated immutable byte string | Currently points at a private LLVM global; it is not a managed string handle |
| `bool` | `i1` | One-bit boolean | Printed through compiler-generated `true`/`false` literals |
| `void` | `void` | No value | Used for statements and the source-level `main` function |

`number` is not an integer ABI type. In particular, `%` is currently lowered
as floating-point remainder in LLVM, while the reference interpreter's current
implementation converts operands to `int64` before calculating remainder. This
semantic mismatch must be resolved and covered by differential tests before
remainder is treated as a fully portable runtime behavior.

### Output operations

`console.log` is the only source-level operation that currently crosses the
runtime boundary. Lowering accepts exactly one argument and emits an `OpPrint`
instruction. The LLVM backend selects the host operation from the checked IR
value type:

| Source value | Generated operation | Observable output |
| --- | --- | --- |
| `number` | `printf(ptr @.fmt.num, double value)` | Decimal formatting using C `%g`, followed by `\\n` |
| `string` | `puts(ptr value)` | Bytes up to the first NUL, followed by `\\n` |
| `bool` | `select` between `@.true` and `@.false`, then `puts` | `true\\n` or `false\\n` |

The compiler creates these private LLVM constants:

```llvm
@.fmt.num = private unnamed_addr constant [4 x i8] c"%g\0A\00"
@.true = private unnamed_addr constant [5 x i8] c"true\00"
@.false = private unnamed_addr constant [6 x i8] c"false\00"
```

String literals are emitted as private, NUL-terminated byte arrays. Their
length is based on UTF-8 encoded bytes, not Unicode scalar count. `puts` is a
C string API, so embedded NUL bytes cannot be represented faithfully in the
current output path. There is no flushing, error propagation, formatting
options, or multi-argument `console.log` contract yet.

The return value of both `printf` and `puts` is intentionally discarded. A
negative C-library return value therefore does not become a Scriptgo runtime
diagnostic in the MVP.

### Startup and exit status

Clang and the host linker provide process startup. The generated `main` does
not receive `argc` or `argv`, and the MVP has no startup hook, environment
initialization, signal policy, or shutdown callback.

Normal completion returns process status `0`. Compilation, LLVM emission,
Clang invocation, and linker failures are compiler/toolchain failures handled
outside the runtime. Runtime failures are not yet modeled.

### Allocation and ownership

The MVP does not allocate runtime-managed values. Numeric and boolean values are
passed by value. String literals point to static immutable storage owned by the
generated module and remain valid for the entire process. Generated code must
not free, mutate, or retain an assumed heap ownership claim for these pointers.

This rule does not define ownership for future strings, arrays, objects, or
errors. Those features require a separate representation and lifecycle
contract before they are added to lowering or LLVM emission.

## Boundary Responsibilities

The dependency direction is:

```text
frontend -> lowering -> typed IR -> LLVM backend -> host C ABI/toolchain
```

- `internal/frontend` reports checked source data and source-anchored
  diagnostics. It does not choose runtime layouts.
- `internal/lowering` decides whether a source construct is in the native
  subset and makes required runtime operations explicit in IR.
- `internal/ir` describes values and operations without importing C, LLVM, or
  TypeScript-Go APIs.
- `internal/backend/llvm` translates verified IR into target-specific calls
  and declarations.
- `internal/runtime` owns this contract and, later, the linked implementation.
- `internal/interpreter` provides semantic-oracle behavior for tests; it is not
  linked into native programs and must not be imported by the runtime.

## Unsupported Runtime Surface

The following are intentionally outside the MVP ABI:

- mutable or dynamically allocated strings;
- arrays, objects, classes, property lookup, and prototype behavior;
- `null` and `undefined` representations;
- exceptions, stack unwinding, and panic/abort policy;
- async scheduling, promises, timers, and event-loop integration;
- garbage collection, reference counting, or explicit release operations;
- Node.js APIs, npm packages, filesystem, networking, and FFI;
- variadic or multi-argument `console.log` behavior.

Unsupported features must be rejected by the native subset gate before backend
generation. They must not be silently represented as C pointers or host calls.

## Requirements For A Linked Runtime

Before replacing the temporary host ABI with a project-owned runtime library,
the implementation must document and test at least:

1. ABI version and target compatibility, including calling convention, pointer
   width, alignment, and data layout assumptions.
2. Exact layouts for strings, arrays, objects, boxed values, `null`, and
   `undefined`.
3. Ownership transitions for every pointer-returning and pointer-consuming
   operation, including failure paths and shutdown.
4. Error representation and propagation: status returns, exceptions, or an
   explicit process-failure policy.
5. Startup and shutdown hooks, including argument/environment access if they
   become part of the language subset.
6. Compatibility tests shared by the interpreter and every native backend.

The linked runtime should expose narrow semantic operations rather than leak
interpreter data structures into lowering or backend code. For example, a
future string concatenation operation may be an ABI call, but its implementation
must remain in the runtime and its source-level eligibility must remain in
lowering.

## Testing And Change Policy

Runtime-affecting changes require tests at the boundary that owns the behavior:

- LLVM emission tests verify declarations, type mapping, constants, and call
  signatures.
- Lowering tests verify that source operations produce the intended IR
  operation and reject unsupported calls.
- Interpreter tests provide the reference observable result.
- Compiler end-to-end tests verify native output, newline behavior, and exit
  status where applicable.
- ABI tests must cover every new native runtime operation before it is enabled
  in the subset.

When the contract changes, update this document, the native subset policy,
and the relevant roadmap milestone in the same change. Keep generated
executables and temporary LLVM output out of source control.
